**太长不看**

对一个长期运行在 Codex OAuth 上的器灵来说，提示缓存几乎决定了大部分成本。而缓存要起作用，同一工作流发出的每一次请求都必须携带**同一个**稳定身份。LingTai 把 `session-id`、`thread-id`、`prompt_cache_key` 对齐到同一个持久的「按器灵」身份——而不是绑定到逐次调用的 id、工具调用 id、随机 UUID，或每次凝蜕都会变的时间戳。在此基础上，我们进一步打磨了这个身份**何时**才允许轮换:依据的是生态里的真实证据，而不是把见到的每个请求头都抄过来。

</div>

## 为什么缓存亲和性重要

当一个器灵连续运行数小时乃至数天，它发出的几乎每一次请求都共享一段又长又几乎相同的前缀:系统提示、工具定义、不断累积的对话历史。如果每一轮都按全价重新计费这段前缀,成本将不可承受。提示缓存正是为此而生——供应商保留一份「热」的前缀副本,在后续命中时以极低折扣计费缓存 token。

但缓存要有用,你的下一次请求必须落到**同一份**热副本上。这个路由由请求携带的身份决定。如果每一轮都换一个身份,在缓存看来,每次请求都像是一段全新的对话:前缀被重新摄入,折扣蒸发,成本可能翻好几倍,而行为上毫无收益。

所以整件事的关键就是:**让身份在多次调用之间保持稳定,好让缓存一直认得你。** 这就是我们说的*缓存亲和性*——请求对它自己养出来的那份热副本的亲和力。

## 稳定身份契约

官方 Codex 客户端在这里给了清晰的信号。在它的主路径上,会话身份、线程身份与缓存键并不是三个互相独立的值——它们被绑在一起,都从同一个底层的线程身份派生而来。换句话说,「我作为一个会话是谁」「这是哪一条对话线程」「我属于哪个缓存桶」这三个问题,由**同一个**持久句柄回答。

LingTai 采用了同样的契约:

```text
session-id  ==  thread-id  ==  prompt_cache_key  ==  同一个稳定的「按器灵」身份
```

关键词是**稳定**。这个身份必须锚定在持久的东西上——器灵 / 工作流本身——而不能锚定在任何会频繁变动的东西上。具体来说,我们**不**用它派生自:

- 最近一次的 API 调用 id;
- 最近一次的工具调用 id;
- 每次请求新生成的随机 UUID;
- 或者凝蜕/刷新的时间戳。

这些每时每刻都在变,而这恰恰是对缓存键最不该做的事。一个在每次工具调用时都重新设键的器灵,等于每分钟几十次地告诉缓存「我是个新人」。LingTai 的做法是:从解析出的器灵身份派生出一个简短而稳定的哈希,并在多次调用之间复用——并且关键在于,**跨凝蜕**复用。凝蜕会清除器灵的对话,但它的身份长存,因此它的缓存亲和性也应当长存。

## 读生态——有用,但要存疑

Codex OAuth 是一个热闹的生态。我们梳理了一批与 Codex OAuth 后端对话的公开 harness、网关与运行时,大致分成两类:

1. **套壳官方二进制或复用其鉴权状态。** 这类项目拉起真正的 Codex app-server,或复用它存好的凭据,因此底层的缓存与会话细节大体由官方运行时掌管。
2. **自管 OAuth token,直连后端。** 这类自己构造请求,也就意味着必须自己把缓存身份做对。

成熟与脆弱实现之间的分界线,不在于「用没用 OAuth」,而在于「有没有维护一个**稳定的会话/对话级缓存身份**」。成熟的网关会一致地发送稳定的缓存键以及会话/对话提示;脆弱的要么干脆不发缓存键,要么每次生成一个不稳定的。

我们找到的那个最丰富的公开参考,用了比基线更完整的指纹——在核心三件套之外,还带了若干路由风格的请求头。这确实是有用的*证据*,说明额外的提示可能有意义。但这**绝不**等于可以把整套抄过来。其中一些请求头可能携带官方客户端或窗口相关的语义,另一些可能绑定在某个网关特定的请求塑形策略上。盲目照抄,等于冒着发送一堆无意义、被拒绝、甚至帮倒忙的值的风险。正确姿态是:把第三方请求头集合当成「待验证的假设」,放在能力开关后面逐一实验,而不是当成规范写死。

## 为何值得如此小心:一次公开的回归

上面那条告诫并非纸上谈兵。一个广为人知的 Codex OAuth 运行时经历过一段很有教益的循环,全程可在它的公开历史里看到:

- 它从 Codex 传输诞生之初就带着一个 body 层的缓存键。
- 后来它加入了 HTTP 请求头形式的路由提示,以更精确地划定缓存范围。
- 在修复一个与此无关的「不支持的参数」后端报错时,某次改动剥掉了请求的额外请求头——结果连同那个惹事的字段一起,把真正的缓存亲和性 HTTP 请求头也误删了。
- 据报告,缓存命中率从约 **~95%** 崩到了 **~20–30%**,成本影响严重;之后的修复才把这些请求头作为正经的 HTTP 头恢复回来,同时把缓存键留在 body 里。

这条教训可以干净地推广:**body 字段**与 **HTTP 请求头**之间存在真实的边界,二者不可互换。悄悄删掉缓存亲和性*请求头*,即便行为看上去毫无变化,也可能让成本爆炸。缓存身份值得与任何其他成本攸关的契约一样的小心——以及一样的回归测试。

这个模式也不是某个项目独有的一次性 bug。追溯这些运行时的血缘可以看到,稳定的缓存亲和性处理作为一个工程主题,在整个家族里反复出现:被继承、被重新推导,而非一次性发明。它是个长期课题,不是脚注。

## LingTai 最终的落点

上面的基线——`session-id == thread-id == prompt_cache_key`,全部绑定到同一个稳定的「按器灵」身份——是地基。留待解决的是:这个身份**何时**(如果有的话)才该改变。永远固定很简单,但很脆;逐次调用就换,又正是我们极力避免的原罪。答案是一套刻意收窄的轮换策略:

- **在启动与刷新时**,适配器盖一个新的纪元戳,派生出一个新的当前亲和 id。一次真正的新运行,获得一条干净的缓存血缘。
- **在缓存停滞时**,id 就地轮换——但仅当缓存信号本身表明它卡住了。触发条件保守:最近**八**次为正的缓存 token 读数完全逐字节相同,这暗示热副本已不再有用地增长。只有此时,当前 id 才轮换。
- **没有「一次性临时 id」。** 早期探索尝试过「某一次请求用一个用后即弃的 id,然后立刻还原」的路径;这条被砍掉了。轮换之后,后续请求就直接沿用新的当前 id。任何时刻,只有一个身份。

全程,三字段不变式成立:请求 body 的缓存键与两个 REST 请求头携带**同一个**当前 id,用量元数据记录的也是实际用到的那个 id——这样缓存行为始终可观测,又不暴露任何敏感信息。

最终的结果是:一个器灵的缓存亲和性默认持久、能扛过凝蜕,并且只在两个真正需要换身份的时刻才换到新身份:一次真正的全新开始,或者一份已被证明不再有帮助的缓存。

## 小结

- **提示缓存是一份成本契约,不是免费的优化。** 对长跑器灵来说它主导账单;请认真对待。
- **一个持久身份,跨调用、跨凝蜕复用。** 把它绑到器灵/工作流上,绝不绑到逐次调用 id、工具 id、随机 UUID 或会变的时间戳。
- **请求头与 body 字段是不同的面。** 丢掉缓存亲和性*请求头*会悄无声息地毁掉命中率——用测试守住它。
- **向生态学习,但别照搬。** 第三方请求头集合是「待验证的线索」,不是「待克隆的规范」。
- **罕见地、且只在有信号时轮换身份**——真正的启动/刷新,或一份已被证明停滞的缓存——而非每次调用都换。
